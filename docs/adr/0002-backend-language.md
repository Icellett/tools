# ADR-0002: Использовать Python и Django для серверной части

**Статус:** принято как проектное решение  
**Основание:** требования и модель предметной области TutBerry

## Контекст

Серверная часть TutBerry должна обеспечивать операции с объявлениями, заявками, календарём, платежами и отзывами. В существующих требованиях и README выбран Python 3.11+ и Django. Архитектурная запись фиксирует последствия этого выбора и его альтернативы.

## Движущие факторы

- `C-01`: Python (Django), React, PostgreSQL.
- `FR-01`–`FR-07`: каталог, бронирование, расчёт стоимости, платежи и споры.
- Требуется удобная реализация REST API и ролей пользователей.

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
|---|---|---|
| **Python 3.11+ и Django** | ORM, миграции, админ-панель, встроенные механизмы авторизации, совместимость с существующими документами | Синхронные операции и тяжёлые запросы требуют внимания к производительности |
| Python и FastAPI | Удобная типизация API, асинхронные обработчики | Потребуется самостоятельно собрать больше инфраструктуры, расходится с `C-01` |
| Node.js и NestJS | TypeScript на сервере и клиенте, модульная структура | Переход на другой язык и нарушение `C-01` |

## Решение

Серверная часть строится на **Python 3.11+ и Django**, API предоставляется через Django REST Framework. Данные хранятся в PostgreSQL 14+. Клиентская часть остаётся на React 18 и TypeScript. **Определяющий довод:** соответствие `C-01` и существующей спецификации проекта.

## Последствия

**Положительные:** Не требуется менять согласованный стек; можно использовать Django ORM и админ-панель для модерации.

**Отрицательные:** Производительность запросов зависит от правильных индексов и оптимизации ORM; Django REST Framework добавляет зависимости.

**Условие пересмотра:** Изменение обязательного технологического ограничения либо выявленная невозможность выполнить критическое требование средствами Django.
