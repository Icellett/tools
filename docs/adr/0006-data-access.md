# ADR-0006 — Доступ к данным и защита бронирований

- Статус: принято для ЛР 4А
- Контекст: TutBerry, Django и PostgreSQL

## Контекст

В ЛР 3 хранилище реализовано через Django ORM, а сценарий `BookingService` зависит от порта `BookingRepository`. Проверка пересечения дат в сценарии не защищает от двух одновременных записей: оба запроса могут увидеть свободный интервал.

## Решение

Для операций бронирования используется `SqlBookingRepository` с SQL-запросами, написанными вручную, и параметрами через `django.db.connection.cursor()`. Это соответствует согласованному Django-стеку, хотя отличается от примера методички с `asyncpg` и Alembic.

Миграция `0002_booking_no_overlap` добавляет PostgreSQL `EXCLUDE USING gist` по объявлению и диапазону дат. Даты аренды включают последний день, поэтому диапазон в SQL задаётся как `daterange(start_date, end_date + 1, '[)')`. Отменённые брони исключены из ограничения.

Границей транзакции владеет обработчик API: `transaction.atomic()` и `select_for_update()` для объявления. Хранилище не создаёт самостоятельных транзакций. Ошибка ограничения PostgreSQL `23P01` переводится в `BookingError`, а API возвращает HTTP 409.

## Последствия и компромиссы

- Предметная логика `BookingService` не зависит от SQL и остаётся без изменений.
- Правило непересечения обеспечивается базой даже при состязании запросов.
- Применение/откат миграций проверяется CI тремя циклами.
- Используется синхронный драйвер Django, а не асинхронный пул из примера методички.
- Старый ORM-адаптер остаётся в репозитории для истории ЛР 3; основной API использует SQL-адаптер.
- Данные и схемы остальных ресурсов модели ЛР 2Г ещё предстоит перенести.
