# ADR-0005: Проверять доступность инструмента транзакционно перед бронированием

**Статус:** принято как проектное решение  
**Основание:** требования и модель предметной области TutBerry

## Контекст

Между просмотром выдачи и отправкой заявки даты могут занять. Кэш ускоряет поиск, но его состояние может устареть. Нужна стратегия, которая не допускает двойного бронирования независимо от способа отображения каталога.

## Движущие факторы

- `FR-01`: поиск только доступных инструментов на выбранные даты.
- `FR-04`: владелец блокирует даты.
- `FR-07`: заявка не создаётся на занятый интервал.
- `NFR-01`: p95 поиска не более 300 мс при 50 000 объявлениях и 20 запросах в секунду.
- `BR-02`: отсутствие двойных подтверждённых броней.

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
|---|---|---|
| **Индексы и транзакционная проверка при создании заявки; кэш — только при необходимости** | Нет дополнительной службы на первом этапе; источник истины — PostgreSQL; корректность не зависит от кэша | Требует продуманной блокировки и нагрузочных тестов |
| Кэш выдачи на 5 секунд без проверки в транзакции | Быстрая выдача | Возможны конфликтующие заявки и некорректное подтверждение |
| Кэш с инвалидацией и транзакционной проверкой | Снижает чтения базы и сохраняет корректность | Потребуются служба кэша и логика сброса |

## Решение

Источником истины для доступности остаётся **PostgreSQL**. Поиск использует индексы по объявлению, статусу и датам. При создании заявки и её подтверждении сервер **в транзакции повторно проверяет пересечение интервалов** и блокировки владельца. Для одного объявления конкурентные операции сериализуются блокировкой строки объявления (`SELECT ... FOR UPDATE`) либо эквивалентным механизмом. При конфликте возвращается `409 Conflict`, как предусмотрено API. Кэширование поиска не вводится без подтверждённой необходимости по результатам нагрузочного теста; при добавлении кэша проверка в транзакции сохраняется. **Определяющий довод:** нельзя жертвовать корректностью брони ради скорости выдачи.

## Последствия

**Положительные:** Двойное подтверждение одного интервала предотвращается на уровне серверной операции; не требуется Redis на первом этапе.

**Отрицательные:** Блокировки увеличивают время ожидания при конкурентных заявках; достижение p95 300 мс требует измерений и настройки индексов.

**Условие пересмотра:** Нагрузочные тесты покажут превышение `NFR-01` или изменятся правила удержания дат и конкурентного подтверждения.
