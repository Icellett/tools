# Аудит тестируемости (ЛР 3Б)

## Слои и границы

- **HTTP**: `tutberry/views.py`, `tutberry/api_booking.py` — DRF и сериализация запросов.
- **Сценарии**: `tutberry/services/booking_service.py` — расчёт стоимости и координация зависимостей.
- **Предметная область**: `tutberry/domain/` — агрегаты и инварианты, без Django.
- **Адаптеры**: `tutberry/adapters/` — in-memory дубль и Django ORM.
- **Хранение**: `tutberry/models.py` и `tutberry/migrations/`.

## Швы и тестовые дубли

1. `override_settings` для конфигурации Django.
2. `django.test.Client` и `rest_framework.test.APIClient` для HTTP.
3. `InMemoryBookingRepository` вместо реальной БД в модульных тестах.
4. `FixedIds` для предсказуемых идентификаторов.
5. `SpyNotifier` для проверки уведомления без внешней интеграции.
6. PostgreSQL в CI для интеграционного теста `POST /api/bookings`.

## Проверяемые правила

- Дата окончания не раньше даты начала.
- Пересечение периодов, включая границы.
- Расчёт аренды за число календарных дней и учёт залога.
- Невозможность одобрить отменённую бронь.
- Модерация объявления до активации.
- Подтверждение платежа только с идентификатором провайдера.
- Нельзя создать две брони с пересекающимися датами для одного объявления.
- API требует авторизации и берёт цену из записи объявления.

## Паттерны и рефакторинг

Repository, Dependency Injection и Value Object. Подробности — [docs/refactoring-notes.md](../refactoring-notes.md).

## Известные ограничения

Отсутствует интеграция с платёжным шлюзом и реальным сервисом уведомлений; `NoopNotifier` ничего не отправляет. В CI нет отдельной автоматической проверки запрещённых зависимостей между слоями или терминов единого языка. Для конкурентных запросов используется блокировка строки объявления внутри транзакции PostgreSQL; другие сценарии изменения календаря должны соблюдать тот же протокол блокировок.
