# Агрегаты предметной области — TutBerry


## 1. Объявление (Listing)

**Корень:** `Listing`. **Контекст:** Каталог. **Внешние ссылки:** `owner_id` (учёт пользователей).

| Элемент | Вид | Назначение |
|---|---|---|
| `Listing` | Сущность, корень | Объявление со своим ID и жизненным циклом |
| `ListingStatus` | Значение | `draft`, `moderation`, `active`, `archived` — соответствует ER-модели |
| `Money` | Значение | Цена за сутки и залог, валюта и неотрицательная сумма |
| `BlockedPeriod` | Значение внутри агрегата | Ручная блокировка дат владельцем |
| `ListingPhoto` | Ссылка на файл изображения | Изображение инструмента |

### Инварианты

1. Цена за сутки и залог неотрицательны; цена аренды для опубликованного объявления положительна.
2. Отправить объявление на модерацию можно только с обязательными полями, предусмотренными US-01.
3. Публикация возможна после одобрения модератором; черновик не попадает в публичный поиск.
4. Блокировка имеет корректный интервал дат (`end_date >= start_date` при включительных датах).
5. Изменять объявление может его владелец; одобрять — модератор. Проверка роли выполняется на уровне сценария с данными пользователя.

### События

`ListingCreated`, `ListingSubmitted`, `ListingApproved`, `ListingRejected`, `ListingArchived`, `ListingDatesBlocked`, `ListingDatesUnblocked`.

### Что не является инвариантом `Listing`

«Нет пересекающихся подтверждённых броней» требует проверки других экземпляров `Booking`; это правило сценария бронирования, а не одного объявления. Публикация не должна загружать все брони объявления.

## 2. Бронь (Booking)

**Корень:** `Booking`. **Контекст:** Бронирование. **Внешние ссылки:** `listing_id`, `tenant_id` и ID владельца; другие агрегаты не вкладываются в бронь.

| Элемент | Вид | Назначение |
|---|---|---|
| `Booking` | Сущность, корень | Заявка/сделка с ID и статусом |
| `RentalPeriod` | Значение | Пара календарных дат аренды |
| `BookingPrice` | Значение | Зафиксированные стоимость и залог на момент заявки |
| `BookingStatus` | Значение | `pending`, `approved`, `paid`, `active`, `completed`, `cancelled`, `disputed` |
| `CancellationReason` | Значение | Причина отмены |

### Инварианты

1. Период аренды корректен: конец не раньше начала; при расчёте число оплачиваемых суток положительно.
2. Зафиксированные суммы аренды и залога неотрицательны и не меняются задним числом из-за изменения цены объявления.
3. Отменённую бронь нельзя повторно подтвердить или перевести в аренду без нового сценария.
4. `active` допускается только после подтверждения оплаты и передачи инструмента по правилам жизненного цикла брони.
5. `completed` допускается после фиксации возврата с учётом отсутствия открытого спора.
6. Если статус `cancelled`, причина отмены заполнена — согласуется с существующей ER-моделью.

### События

`BookingCreated`, `BookingApproved`, `BookingRejected`, `BookingCancelled`, `BookingPaid`, `ToolHandedOver`, `ToolReturned`, `BookingCompleted`, `DisputeOpened`, `DisputeResolved`.

### Не инварианты агрегата

- Свободен ли инструмент на выбранные даты: нужны другие брони и блокировки объявления. Проверяется сервисом `BookingService` в транзакции PostgreSQL, включая конкурентные запросы.
- Успешно ли платёжный провайдер удержал деньги: источник истины — `Payment` и подтверждённый статус провайдера; `Booking` реагирует на событие.

## 3. Платёж (Payment)

**Корень:** `Payment` (логическая операция оплаты по брони). **Контекст:** Платежи. **Внешняя ссылка:** `booking_id`.

| Элемент | Вид | Назначение |
|---|---|---|
| `Payment` | Сущность, корень | Платёж и его подтверждённое состояние |
| `PaymentStatus` | Значение | `pending`, `success`, `failed`, `frozen` (из существующей ER-модели) |
| `PaymentAmount` | Значение | Сумма операции |
| `GatewayReference` | Значение | ID операции у провайдера |
| `Transaction` | Сущность/запись операции | `rent_payment`, `deposit_hold`, `deposit_refund`, `payout` |

### Инварианты

1. Сумма каждой операции положительна, кроме случаев, отдельно разрешённых спецификацией провайдера.
2. Одна и та же внешняя операция не применяется повторно при повторном webhook; используется уникальный ID операции и/или ключ идемпотентности.
3. Нельзя освободить больше залога, чем подтверждено к удержанию, с учётом ранее выполненных операций.
4. Нельзя отмечать платёж успешным только по действию пользователя: нужен подтверждённый ответ провайдера.
5. Финансовые статусы не подменяются статусами брони.

### События

`PaymentInitiated`, `PaymentConfirmed`, `PaymentFailed`, `DepositHeld`, `DepositReleased`, `DepositAllocated`, `PayoutCompleted`.

### Граница и внешняя интеграция

`PaymentGateway` — порт, адаптер которого переводит ответы конкретного провайдера во внутренние состояния. Удержание и распределение средств выполняются через возможности выбранного провайдера; доменная модель не зависит от его внутренних названий операций.

## Почему именно три агрегата

`Listing` живёт независимо от сделок. `Booking` управляет одной заявкой и не включает объявление целиком. `Payment` зависит от подтверждений внешнего сервиса и не может атомарно изменяться вместе с бронью. Изменения между агрегатами координируются сценариями и событиями, а не общей транзакцией всех объектов.

## Согласование с моделью данных

| Агрегат | Таблицы из текущей ER-модели | Примечание |
|---|---|---|
| `Listing` | `LISTINGS`, `LISTING_AVAILABILITY` | Блокировки дат принадлежат объявлению |
| `Booking` | `BOOKINGS` | Сообщения и отзывы в отдельной области ответственности |
| `Payment` | `TRANSACTIONS` | Один платёжный процесс может содержать несколько операций |
