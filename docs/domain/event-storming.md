## Ограниченные контексты

- **Каталог:** создание, модерация, публикация объявления, ручная блокировка дат. Собственные правила и жизненный цикл `Listing`.
- **Бронирование:** выбор интервала, расчёт суммы, заявка, решение владельца, передача, возврат, спор. Собственный жизненный цикл `Booking`.
- **Платежи:** платёжные операции, статусы провайдера, удержание и освобождение залога. Не подменяет статус брони.
- **Учёт пользователей:** регистрация, роли, профиль и идентификаторы сторон.
- **Уведомления:** доставка сообщений о событиях; сбой доставки не отменяет сделку.
- **Репутация:** отзывы после завершения сделки. Отдельная модель может быть уточнена позднее.

**Почему границы такие:** объявления существуют без бронирований; бронирование ссылается на объявление по ID; платёжная операция имеет собственные внешние статусы и может завершиться не одновременно с бронью; пользователи существуют независимо от объявлений. Все контексты могут размещаться в одном Django-приложении как модули — контекст не равен отдельному сервису.

**Отклонённый вариант:** объединить каталог, бронь и платёж в один агрегат «Сделка». Он потребовал бы изменять объявление и платёж при каждом действии с бронью, усложнил бы конкурирующие бронирования и смешал разные правила.

## Связи контекстов

| Откуда | Куда | Вид | Что передаётся | Обоснование |
|---|---|---|---|---|
| Учёт пользователей | Каталог / Бронирование | Поставщик — потребитель | `user_id`, роль | Общая модель идентификации, без копирования профиля |
| Каталог | Бронирование | Поставщик — потребитель | `listing_id`, цена, блокировки | Бронирование использует данные объявления, но хранит сумму сделки отдельно |
| Бронирование | Платежи | Поставщик — потребитель | `booking_id`, сумма, залог, запрос операции | Платежи не управляют правилами выбора дат |
| Платёжный провайдер | Платежи | Уровень предотвращения искажений (ACL) | Внешний ID и статус операции | Внешние статусы переводятся во внутренние `PaymentStatus` |
| Бронирование / Платежи | Уведомления | Публикация события / потребитель | ID события, ID пользователя, тип | Ошибка почты не отменяет бронь или платёж |
| Бронирование | Репутация | Поставщик — потребитель | `booking_id`, факт завершения | Отзыв допустим только по завершённой сделке |

**ACL для платёжного провайдера:** интерфейс `PaymentGateway` принимает команды оплаты, удержания и освобождения; адаптер переводит внешний ответ в `PaymentStatus`. Доменная модель не зависит от названий статусов конкретного провайдера.

## Предложение о структуре кода (вход для ЛР 2В)

Рекомендуется модульный монолит Django с модулями `users`, `catalog`, `bookings`, `payments`, `notifications`, `reviews`, а React — как отдельный интерфейс. Общение между модулями через явно заданные сервисы/события и ID, без прямого изменения чужих агрегатов. Это **предложение**, архитектурное решение будет оформлено в ЛР 2В.

## Что уточнить в требованиях после командной сессии

1. Уточнить срок удержания дат у заявки (US-05, FR-07).
2. Согласовать различие между отметкой возврата и подтверждением состояния инструмента (US-10/US-11).
3. Уточнить фактический механизм удержания/возврата средств у провайдера (FR-03).
4. Согласовать обязательные фотографии при передаче и возврате (CJM и FR-05).
