# Стратегия тестирования TutBerry (ЛР 5)

## Цель и область
Стратегия определяет, как проверяются требования платформы аренды инструментов TutBerry, какие тесты относятся к каждому уровню, какие метрики фиксируются и какие риски пока остаются открытыми. Источник требований: [docs/requirements.md](../requirements.md).

## Уровни и правила распределения

| Уровень | Что проверяется | Примеры в текущем наборе |
| --- | --- | --- |
| Модульный | Правила без БД и HTTP: сроки аренды, стоимость, переходы статусов, ошибки | `tests/test_booking_domain.py`, `tests/test_booking_service.py` (тесты без внешних зависимостей) |
| Интеграционный | Работа с PostgreSQL, Django API, права доступа, пересечения броней и блокировок | `tests/test_booking_api.py`, `tests/test_sql_booking_repository.py`, `tests/test_listing_availability.py` |
| Контрактный | Соответствие ответов API опубликованному OpenAPI-контракту | `tests/test_openapi_contract.py` |
| Сквозной | Проверка связанного пользовательского сценария через доступные слои приложения | `tests/test_system.py` — уточнять фактическую глубину сценария по коду теста |
| Нагрузочный | Время отклика поиска при заданной интенсивности и объёме данных | Планируется `tests/load/`; результат пока не измерен |

Правило выбора уровня: бизнес-правило без внешней системы проверяется модульно; реальное взаимодействие с БД или HTTP — интеграционно; схема ответа — контрактно; связанный путь пользователя — сквозным тестом. Дублировать одинаковое утверждение на нескольких уровнях не требуется.

## Техники проектирования
- **Классы эквивалентности:** допустимый период аренды; обратный период; занятые и свободные даты; авторизованный и неавторизованный пользователь.
- **Граничные значения:** начало и конец периода, соприкасающиеся даты, однодневная аренда, цена и залог на допустимых границах.
- **Таблицы решений:** владелец/арендатор × статус объявления × наличие пересечения × результат создания брони.
- **Переходы состояний:** создание, подтверждение, оплата, выдача, завершение и отмена брони; запрет недопустимых переходов.
- **Негативные сценарии:** чужая бронь, некорректный UUID, повторная бронь на занятые даты, блокировка владельцем.

Подробные случаи и ожидаемые результаты должны фиксироваться в `test-design.md`, а не выводиться только из названий тестов.

## Автоматические проверки
Workflow: `.github/workflows/ci.yml`. На push в `main` и pull request выполняются Ruff, mypy и pytest с PostgreSQL. Текущий локально измеренный результат до добавления этой стратегии: **25 пройденных тестов**, покрытие **93%** (441 оператор, 33 пропущено). Это базовое значение, не гарантия отсутствия дефектов.

Команды для воспроизведения:
```sh
python -m ruff check tutberry tests --no-cache --exclude tutberry/migrations --ignore EXE002,RUF012
python -m mypy tutberry --ignore-missing-imports --no-incremental --cache-dir=/tmp/mypy_cache --exclude 'migrations/'
python -m pytest tests/ --cov=tutberry --cov-report=term-missing -p no:cacheprovider
```
Для pytest нужна доступная PostgreSQL и корректный `DATABASE_URL`.

## Пороги качества
| Показатель | Целевое правило | Состояние |
| --- | --- | --- |
| Ruff | Нет ошибок по принятой конфигурации | Проверяется CI |
| mypy | Нет ошибок по принятой конфигурации | Проверяется CI |
| pytest | Все тесты проходят | Проверяется CI |
| Покрытие строк | Не ниже 80% | Цель; **пока не блокирует CI** |
| Время полного прогона | Не более 60 секунд | Цель; **пока не блокирует CI** |
| Мутационный балл | Установить после базового замера | Не измерен |
| Хрупкие тесты | Нет известных нестабильных тестов без исправления | Повторные прогоны ещё не документированы |
| Нагрузка NFR-01 | p95 поиска ≤300 мс при 20 запросах/с и 50 000 объявлениях | Не измерено |

Численные пороги покрытия и времени — начальные целевые значения, требующие автоматизации. Нельзя считать их выполненными только по зелёному статусу CI.

## Что пока не проверяется
- Реальные операции платёжного провайдера и эскроу (FR-03): тестовый шлюз не доказывает поведение внешнего провайдера.
- Полный процесс разрешения споров (FR-05): нужны отдельные приёмочные сценарии.
- Месячная доступность 99,9% (NFR-02): требует длительного мониторинга.
- Шифрование персональных данных и TLS 1.3 в реальном развёртывании (NFR-03): нужны конфигурационный аудит и проверка окружения.
- Производительность при 50 000 активных объявлениях (NFR-01): без подготовленных данных и k6 нельзя заявлять выполнение.
- Доступность интерфейса, кроссбраузерность и реальная работа пользователя с React: серверные тесты этого не покрывают.

## Управление хрупкими тестами
Повторять весь набор в одинаковых условиях, отдельно проверять зависимость от даты, порядка запуска, случайных данных, общей БД и внешних сервисов. Каждый нестабильный случай заносить в `flaky.md` с причиной и исправлением. Автоматический повтор не должен скрывать проблему.

## Проверка способности тестов находить ошибки
Запланировать пять обратимых изменений поведения (граница периода, расчёт стоимости, права владельца, пересечение дат, недопустимый переход статуса). После каждого изменения запускать соответствующие тесты и фиксировать, обнаружили ли они дефект. Не оставлять намеренно испорченный код в `main`.
