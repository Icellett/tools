# Проверка NFR-01: поиск при 50 000 активных объявлениях

## Что реализовано

- `GET /api/listings` — публичный поиск доступных объявлений по обязательным датам `start_date`, `end_date` и дополнительным фильтрам `category`, `location`, `min_price`, `max_price`; результат ограничен 20 записями по умолчанию, максимум 100.
- Активные брони и блокировки владельца исключаются непосредственно SQL-запросом (`Exists`), с учётом пересечения включительных дат.
- В таблицу объявлений добавлены категория, локация и составной индекс для поиска; миграция `0007_listing_search_fields.py`.
- `tests/test_listing_search.py` — интеграционные сценарии проверки исключения занятого объявления, фильтрации и валидации.
- `scripts/seed_nfr01.py` — строго 50 000 активных объявлений в отдельной временной базе GitHub Actions.
- `tests/load/search-nfr01.js` — k6, 20 запросов/с в течение 60 секунд; проверка `p95 < 300 мс`, менее 1% ошибок и отсутствие потерянных итераций.
- `.github/workflows/search-nfr01.yml` — PostgreSQL 17, миграции, заполнение базы, сервер Gunicorn с тремя воркерами и k6; JSON-отчёт сохраняется в артефакт `search-nfr01-summary`.

## Границы проверки

Это измерение серверного API на GitHub-hosted runner, а не реальной эксплуатации и не полная проверка UX. Набор данных синтетический; в нём 50 000 активных объявлений, но в базовом варианте нет большого объёма бронирований и календарных блокировок. Результат нельзя переносить на любые объёмы связанных записей или иные серверы.
