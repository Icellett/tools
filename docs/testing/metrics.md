## 2. Воспроизводимость замеров

Локальная среда: Docker Compose с сервисами `api` (Python 3.13, Django) и `db` (PostgreSQL 17). В образе для разработки зависимости устанавливаются при сборке с `INSTALL_DEV=true`.

```powershell
docker compose build --build-arg INSTALL_DEV=true api
docker compose up -d --no-build --force-recreate api

docker compose exec -e COVERAGE_FILE=/tmp/.coverage api python -m pytest tests/ --cov=tutberry --cov-report=term-missing -p no:cacheprovider

docker compose exec api python -m ruff check tutberry tests --no-cache --exclude tutberry/migrations --ignore EXE002,RUF012

docker compose exec api python -m mypy tutberry --ignore-missing-imports --no-incremental --cache-dir=/tmp/mypy_cache --exclude 'migrations/'
```

В GitHub Actions используется отдельный PostgreSQL 17 и установка `requirements-dev.txt` непосредственно в runner Python 3.13. Файл конвейера: `.github/workflows/ci.yml`.

```text

```

## 5. Нагрузочные измерения NFR-01

Требование из `docs/requirements.md`: поиск должен отвечать не дольше 300 мс для 95% запросов при 50 000 активных объявлениях; интенсивность проверки — 20 запросов/с.

Перед измерением зафиксировать:
- конфигурацию CPU/RAM, версию PostgreSQL, параметры подключения и число записей;
- маршрут поиска, фильтры и распределение запросов;
- время прогрева, длительность основного этапа, долю ошибок, p50/p95/p99;
- план запроса и наличие индексов.

**Результат пока отсутствует.** Нельзя заявлять выполнение NFR-01 по времени ответа на пустой базе или по факту успешного запуска CI.

## 6. Следующие действия

1. Проверить в GitHub Actions новые пороги: покрытие ≥80% и время полного прогона ≤60 секунд.
2. Выполнить пять проверок «на сломанный код» с обязательным откатом.
3. Подготовить нагрузочные сценарии и измерить p95 в воспроизводимых условиях.
4. Провести несколько повторных прогонов для выявления нестабильных тестов; результаты занести в `flaky.md`.
