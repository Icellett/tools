# ЛР 3Б — отчёт о рефакторинге TutBerry

## До

После проектирования ЛР 2 были определены агрегаты `Listing`, `Booking` и `Payment`, но предметная логика не была реализована. В ЛР 3А работали только служебные HTTP-эндпоинты.

## После

1. Правила состояний и проверки сумм вынесены в независимые доменные классы.
2. `RentalPeriod` и `BookingPrice` стали объектами-значениями.
3. `BookingService` координирует проверку дат, расчёт и создание заявки.
4. Введены порты репозитория, генератора ID и уведомителя.
5. Добавлены in-memory дубль, PostgreSQL-адаптер и API создания брони.
6. Интеграционный тест проверяет запись брони и запрет пересечения периодов.

## Применённые паттерны

- **Repository** — интерфейс хранения для сценария бронирования.
- **Dependency Injection** — зависимости передаются сервису извне.
- **Value Object** — объекты периода и цены проверяют собственные инварианты.

## Результаты проверки

GitHub Actions выполнил проверку настроек Django, миграций и тестов (успешный запуск [№ 38](https://github.com/TutBerry/tools/actions/runs/44868425892)). Локальный запуск Docker Compose 21.11.2026 подтвердил работу PostgreSQL и HTTP 200 на `/health` и `/version`. При HTML-запросах была обнаружена ошибка 500 из-за отсутствия DjangoTemplates; она исправлена и `/health` повторно проверен в браузере.

## Ограничения

Платёжный провайдер и реальные уведомления не интегрированы. `InMemoryBookingRepository` используется только для тестов. Отдельные проверки архитектурных границ и единого языка пока не автоматизированы. Использование Django вместо FastAPI по ADR-0002 требует согласования с преподавателем.
