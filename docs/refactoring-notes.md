# ЛР 3Б — рефакторинг предметной области TutBerry

## Точка отсчёта

В ЛР 2 определены три агрегата: Listing, Booking и Payment. В ЛР 3А были созданы HTTP-обработчики без предметной логики. Для первого сценария выбран FR-07 — создание заявки на аренду.

## Аудит тестируемости

- Настройки Django изолируются через override_settings.
- HTTP-обработчики тестируются Django test client.
- Правила предметной области не импортируют Django и не обращаются к БД.
- BookingService получает зависимости через конструктор: BookingRepository, IdGenerator и BookingNotifier.
- Для тестирования используются InMemoryBookingRepository, FixedIds и SpyNotifier.

## Найденные проблемы

Смешивание HTTP, расчёта цены, проверки дат и хранения в одном обработчике затруднило бы тестирование и замену БД. Сценарий вынесен в сервис; инварианты размещены в агрегатах.

## Что сделано

- Value Object: RentalPeriod и BookingPrice проверяют корректность значений.
- Агрегат Booking реализует переходы состояний и запрещает повторное подтверждение отменённой брони.
- Listing управляет отправкой на модерацию и одобрением.
- Payment требует ссылку на подтверждённую операцию провайдера.
- BookingService создаёт заявку после проверки занятости и фиксирует цену.
- Проверки запускаются без настоящей БД, сети и платёжного провайдера.

## Паттерны

1. **Repository**: BookingRepository скрывает хранение данных от сценария.
2. **Dependency Injection**: сервис получает генератор ID и уведомитель через конструктор.
3. **Value Object**: RentalPeriod и BookingPrice инкапсулируют правила корректности.

## Было и стало

До: только HTTP-каркас без сценариев аренды. После: независимая предметная модель, сервис создания брони, тестовые дубли и модульные тесты.

## Что не изменилось

ADR-0002: Python + Django REST Framework + PostgreSQL. Объекты Listing, Booking и Payment остаются независимыми агрегатами.

## Ограничения и дальнейшая работа

InMemoryBookingRepository предназначен только для тестов. Он не гарантирует защиту от одновременных конкурентных бронирований; для этого требуется PostgreSQL-адаптер с транзакциями и блокировками. Сценарий пока не подключён к публичному HTTP API. Подключение платежного провайдера и подтверждение реальных платежей не реализованы. Полное соответствие требованию методички о FastAPI требует согласования Django с преподавателем. Реальный прогон тестов и контейнерной сборки ещё не подтверждён.
