# Обзор архитектуры TutBerry

## Назначение и границы системы

TutBerry — веб-платформа аренды ремонтного инструмента между арендаторами и владельцами. Арендатор находит доступный инструмент, рассчитывает стоимость и залог, отправляет заявку, оплачивает аренду, отмечает передачу и возврат. Владелец размещает объявление, управляет доступностью и подтверждает заявки. Модератор проверяет объявления и рассматривает споры.

Ключевые цели — самостоятельное оформление заявок (`BR-01`), предотвращение двойных броней (`BR-02`) и снижение числа споров по залогу (`BR-03`). Нативное мобильное приложение не входит в MVP (`C-02`).

## Структура системы

Архитектурный стиль — модульный монолит (`ADR-0003`). Браузерное приложение на React и TypeScript обращается к REST API на Django. PostgreSQL хранит пользователей, объявления, доступность, бронирования, транзакции, сообщения и отзывы. Внешний платёжный провайдер обрабатывает финансовые операции. Для уведомлений предусматривается почтовый сервис.

Контексты предметной области из ЛР 2Б соответствуют модулям: Users, Catalog, Booking, Payments, Notifications, Reviews. Они являются границами модели, а не отдельными микросервисами.

## Архитектурные решения

| ADR | Выбор | Определяющий довод |
|---|---|---|
| 0001 | MADR в Git | Сохранение причин решений |
| 0002 | Python 3.11+, Django, PostgreSQL | Соответствие `C-01` |
| 0003 | Модульный монолит | Ограниченные сроки и ресурсы |
| 0004 | JWT, ротация refresh-токенов, проверка ролей и владельца | Совместимость с существующим API и защита операций |
| 0005 | Транзакционная проверка дат в PostgreSQL | Корректность брони при конкурентных запросах |

## Качество и способы обеспечения

| Требование | Архитектурная тактика | Способ проверки |
|---|---|---|
| `NFR-01` — p95 поиска ≤ 300 мс, 50 000 объявлений, 20 RPS | Индексы PostgreSQL, анализ SQL, кэш только при необходимости | Нагрузочный тест k6/JMeter |
| `NFR-02` — доступность ≥ 99,9% в месяц | Проверки работоспособности, перезапуск процессов, мониторинг | Метрики доступности за месяц |
| `NFR-03` — защита данных | TLS 1.3, шифрование хранимых персональных данных AES-256, роли и аудит доступа | Проверка конфигурации, тесты прав и безопасности |
| `NFR-04` — сопровождаемость расчётов | Выделенный модуль калькуляции и стабильный API | Ревью изменений и тесты расчёта |
| `NFR-05` — сохранение подтверждённых броней после штатного перезапуска | Постоянное хранение в PostgreSQL, транзакции | Интеграционный тест с перезапуском приложения |

Для каждого NFR предусмотрена тактика; таблица описывает проектные решения, а не результаты измерений.

## Защищённость по замыслу

**Наименьшие привилегии.** Операции с объявлениями и бронями проверяют роль и принадлежность ресурса. Модератор получает доступ только к необходимым для спора материалам. Приложение и база работают с минимально необходимыми правами.

**Защита по умолчанию.** Все API-операции закрыты, кроме явно перечисленных публичных маршрутов, таких как регистрация, вход и просмотр каталога. Ошибка проверки токена приводит к отказу в доступе.

**Эшелонированная защита.** Проверка входных данных на уровне API дополняется предметными инвариантами и ограничениями PostgreSQL. Запросы к базе выполняются параметризованно через ORM. Изменение статусов платежей принимается только после проверки подлинности уведомления платёжного провайдера.

**Защита секретов и персональных данных.** Пароли хранятся как стойкие хеши; ключи и пароли окружения не размещаются в Git. В логах не записываются токены, банковские реквизиты и паспортные данные. Внешние соединения используют TLS. Полные реквизиты банковских карт платформа не хранит.

### Угрозы и меры (STRIDE)

| Угроза | Пример | Мера |
|---|---|---|
| Подмена личности | Чужой запрос с поддельным токеном | Проверка подписи и срока JWT |
| Подмена данных | Изменение чужого объявления | Проверка владельца и прав |
| Отказ от действия | Отрицание решения по спору | Аудит действий с идентификатором пользователя и временем |
| Разглашение | Просмотр чужой сделки | Контроль доступа на уровне объекта |
| Отказ в обслуживании | Частые запросы входа и поиска | Ограничение частоты, мониторинг, лимиты запросов |
| Повышение привилегий | Арендатор вызывает метод модератора | Проверка роли на сервере |

## Осознанные ограничения

Микросервисы не используются из-за стоимости эксплуатации (`ADR-0003`). Кэш поиска не добавляется без измерений (`ADR-0005`). Нативное приложение не разрабатывается (`C-02`). Платёжная интеграция проектируется через внешний API, без хранения полных реквизитов карт (`C-05`).

Реализация, тестирование и эксплуатационные измерения выполняются в следующих частях проекта; этот документ фиксирует архитектуру и её обоснование.
