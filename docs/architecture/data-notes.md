# ЛР 4А — данные TutBerry

## Соответствие модели ЛР 2Г

| Сущность | Реализация | Статус |
|---|---|---|
| USERS | Django `auth_user` + `UserProfileRecord` (0006) | Профиль создан; ссылки `owner_id`, `tenant_id` остаются UUID без FK |
| LISTINGS | `ListingRecord` | Основные поля; описание и категория отсутствуют |
| BOOKINGS | `BookingRecord` | Даты, стоимость, статус и ограничения |
| LISTING_AVAILABILITY | `ListingAvailabilityRecord` (0004) | Блокировки дат, проверка в API и сервис записи |
| TRANSACTIONS | `TransactionRecord` (0005) | Только метаданные, без платёжного шлюза |
| MESSAGES | `MessageRecord` (0005) | Хранение сообщений, без чата/API |
| REVIEWS | `ReviewRecord` (0005) | Хранение оценок и отзывов, без API |

## Ручной SQL и ограничения

Миграция `tutberry/migrations/0002_booking_no_overlap.py` применяет `btree_gist` и PostgreSQL `EXCLUDE USING gist`. Для одного объявления диапазоны `daterange(start_date, end_date + 1, '[)')` не должны пересекаться, если статус не `cancelled`. При этом два соседних календарных дня допустимы, а совпадающий день — конфликт: `RentalPeriod` в предметной модели включает обе границы.

В ЛР 3 сценарий `BookingService` зависит от интерфейса. В ЛР 4 добавлен `SqlBookingRepository` с параметризованными SQL-запросами через Django connection; ORM для операций бронирования не используется. Транзакцией и блокировкой объявления владеет обработчик API. Это адаптация методички к согласованному Django, а не реализация её асинхронного `asyncpg`-примера.

## Проверка

В CI `.github/workflows/lab04-ci.yml` выполняются три цикла применения/отката миграции 0002, затем тесты на PostgreSQL. Локально:

```powershell
docker compose up --build -d
docker compose exec api python manage.py showmigrations tutberry
docker compose exec api python manage.py migrate tutberry 0001
docker compose exec api python manage.py migrate
docker compose exec api pytest -q
```

Последняя команда потребует dev-зависимостей внутри контейнера; в стандартном production-образе они могут отсутствовать. Проверка CI является основным тестовым прогоном.

## Проверенные результаты

- Миграции `0002`–`0006` применяются в CI; выполняется трёхкратный цикл отката к `0001` и повторного применения.
- Интеграционные тесты проверяют календарь, платежные метаданные, сообщения, отзывы и профили, включая ограничения PostgreSQL.
- [Результаты EXPLAIN ANALYZE](../lab04/explain-results.md): 6,917 мс без индекса и 0,031 мс с индексом на тестовом наборе.
- [ADR-0006](../adr/0006-data-access.md) описывает выбор SQL-адаптера и ограничение пересечений.

## Оставшиеся ограничения

- Ссылки пользователей `owner_id`, `tenant_id`, `sender_id`, `receiver_id`, `author_id`, `target_id` не обеспечены внешними ключами на профиль. Связь профиля с `auth_user` — один к одному.
- Не реализованы описание/категория объявления, полная история статусов, интеграция платежей, API сообщений и отзывов.
- Создание блокировок через `set_listing_block` и создание бронирований используют блокировку строки объявления, но прямые записи ORM в обход сервиса не соблюдают этот протокол.
- Добавление новых таблиц — этап **expand**; отдельный безопасный **contract** для замены старых столбцов не выполнялся, поскольку старые столбцы пока нужны работающему коду.
- Измерен индекс `booking_tenant_recent_idx`; эффект частичного `booking_active_start_idx` отдельно не измерялся.

Наличие зелёных CI-проверок подтверждает прохождение автоматических тестов, но не означает готовность всех проектных операций ЛР 2Г.
