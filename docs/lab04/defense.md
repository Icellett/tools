# Лабораторная работа № 4 — материалы для защиты

**Проект:** TutBerry — сервис аренды инструментов.  
**Стек:** Python, Django, Django REST Framework, PostgreSQL 17, GitHub Actions.  
**Ветка:** `lab-04`; изменения представлены в Pull Request № 2.

## Цель

Реализовать слой хранения данных с SQL-операциями и миграциями PostgreSQL, зафиксировать контракт действующего API и проверить его автоматическими тестами.

## ЛР 4А. Выполненные работы

1. Добавлен `SqlBookingRepository`: параметризованные SQL-запросы для операций бронирования, при сохранении независимого интерфейса предметной логики.
2. Миграция `0002` включает `btree_gist` и ограничение `EXCLUDE USING gist`, исключающее пересечение периодов активных бронирований одного объявления. Даты аренды считаются включительно.
3. Миграция `0003` создаёт индексы для запросов по бронированиям.
4. Миграции `0004`–`0006` расширяют схему: календарь доступности, транзакции, сообщения, отзывы, профили пользователей.
5. Для создания бронирования и изменения блокировок календаря предусмотрены транзакции и блокировка строки объявления. Прямые записи в обход сервиса этим соглашением не защищены.
6. В CI проверяются применение и откат миграций, ограничения PostgreSQL и интеграционные сценарии.

### Замер производительности

В изолированной тестовой базе создано 30 000 бронирований. Запрос на получение последних 20 записей арендатора измерен с помощью `EXPLAIN ANALYZE`.

| План | Время выполнения |
|---|---:|
| Без индекса: Seq Scan + Sort | 6,917 мс |
| С индексом: Index Scan | 0,031 мс |

Ускорение в одном тестовом запуске составило около **223 раз**. Результат зависит от объёма, распределения данных и окружения; не является универсальной оценкой. Подробности: [explain-results.md](explain-results.md).

## ЛР 4Б. Выполненные работы

1. Описан фактически реализованный `POST /api/bookings` в [OpenAPI 3.0.3](../api/openapi.yaml).
2. Используется HTTP Basic аутентификация; бронирование собственного объявления запрещено.
3. Для ошибок применяется единая структура `type`, `title`, `status`, `detail` (и необязательное `errors`) с типом `application/problem+json`.
4. Контрактные тесты проверяют коды `201`, `400`, `401`, `403`, `404`, `409`, MIME-типы и схемы ответов.
5. Проверка пересечений дат учитывает существующие бронирования и блокировки владельца.

## Проверка работоспособности

GitHub Actions запускает проверки Django и PostgreSQL на Pull Request № 2. По последнему предоставленному результату CI после исправления OpenAPI проверки были зелёными. Для защиты рекомендуется открыть актуальный запуск и показать журнал `pytest`, шаг миграций и артефакт `lab04-explain-booking`.

## Ограничения

- Пользовательские UUID в объявлениях, бронированиях, сообщениях и отзывах пока не связаны внешними ключами с профилями.
- Платёжный шлюз, чат, API отзывов, JWT и проектные маршруты `/api/v1` не реализованы.
- Продемонстрирован этап расширения схемы (expand); отдельный этап удаления устаревших полей (contract) не выполнялся.
- Прямые изменения календаря в обход сервиса могут нарушить согласование с бронированиями.
- Описанный OpenAPI-контракт относится к одной реально действующей операции, а не ко всем проектным ресурсам.

## Заключение

В ходе лабораторной работы реализованы SQL-доступ к бронированиям, миграции и ограничения PostgreSQL, а также контракт API с автоматическими проверками. Индексирование позволило существенно сократить время тестового запроса. Проверки CI подтвердили работоспособность реализованных сценариев. Оставшиеся ограничения выделены отдельно, чтобы не смешивать готовую функциональность с планируемой.
