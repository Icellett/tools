# ЛР 4Б — контракт TutBerry API

[openapi.yaml](openapi.yaml) описывает **фактически реализованный** `POST /api/bookings`. Проектный каталог операций ЛР 2Г — [resources.md](resources.md); его нельзя считать реализованным API.

## Реализованный контракт

- Путь: `POST /api/bookings` (без префикса `/api/v1`).
- Аутентификация: HTTP Basic через Django REST Framework.
- Вход: `listing_id` (UUID), `start_date` и `end_date` (ISO-даты).
- Успех: HTTP 201, JSON с `id`, `status`, `rent`, `deposit`, `total`.
- Ошибки: HTTP 400, 401, 403, 404, 409; тело `{type,title,status,detail,errors?}`, Content-Type `application/problem+json`.
- Цена рассчитывается на сервере из объявления. Бронирование собственного объявления запрещено; пересечение дат бронирований блокируется ограничением PostgreSQL; блокировки календаря владельца дополнительно проверяются сервисом.

## Контрактные проверки

`tests/test_openapi_contract.py` читает `openapi.yaml`, проверяет объявленные схемы и валидирует ответы действующего API (201, 400, 401, 403, 404, 409), включая MIME-тип ошибок. Тесты запускаются в GitHub Actions на PostgreSQL.

## Особенности безопасности и контракта

- Пользователь может создать бронирование только после аутентификации; собственное объявление бронировать нельзя.
- Одновременные запросы бронирования сериализуются блокировкой строки объявления, а пересечения активных бронирований дополнительно отклоняются ограничением БД.
- Сервис записи блокировок календаря использует ту же блокировку объявления. Прямые изменения таблиц в обход сервиса не покрыты этим соглашением.
- Текущий сериализатор DRF допускает неизвестные поля запроса (игнорирует их). Поэтому контракт не объявляет `additionalProperties: false`.
- Реализация не включает отдельную модель разрешений для всех ролей, JWT, rate limiting и полноценные CRUD-операции.

## Границы реализации

JWT, `/api/v1`, каталог, платежи, чат, модерация и остальные операции из [resources.md](resources.md) пока не реализованы. Текущий набор контрактных тестов проверяет документированные ответы одной операции, но не является полной проверкой всего OpenAPI 3.0 и всех сценариев безопасности.

Изменения в контракте необходимо вносить одновременно с кодом и тестами. Несовместимые изменения требуют отдельной версии API.
